# REQ — release-pipeline

## 1 概述
### 1.1 需求背景 [冻结]
到 v2.4.1 为止，一个改动要经过：本机跑检查、推送，GitHub 上闸门跑完（约 8 分钟），合并到 main 后闸门**再跑一遍**，然后在 VPS 上现场构建镜像、替换容器，最后访问 `localhost:3002/` 确认有响应。部署之后的核对都靠手动：线上 SHA、对生产跑运行时套件、打 tag。

v2.4.0 暴露了四个问题：
- **生产环境只能在生产上验。** 「一次真实输入 + 真机」的检查只能在笔记本上做：要把生产的公开值放到本机、改 Mac 代理的 DNS、开一个局域网服务器外加防火墙例外。nginx 和 Cloudflare 不在任何检查路径上。v2.4.1 那个只在生产出现的 502（登录后的响应头超出 nginx 的缓冲），就是这样漏出去的。
- **CI 从来不是拦截者。** 52 次运行，拦截 0 次，拦截全发生在本机。同一个改动的闸门却要跑四遍：分支 push、PR、main 上的 Check、Deploy 里的调用。
- **出了事退不回去。** 部署失败只会打印日志；VPS 上没有上一个版本的镜像。
- **镜像里有密钥。** Next 的 standalone 输出会复制 `.env`，所以生产镜像里有一份含 service-role 密钥的 `.env`。镜像从没离开过 VPS，所以还没泄露，但它堵死了「在别处构建」这条路。

project-goodman 已经在同一台 VPS 上跑着预发布，但它只在 `127.0.0.1` 上，不经过 nginx，没法用真机访问。本版参照它的形态，但不照搬。

### 1.2 范围
- 做：
  - 镜像不含 `.env`，在 CI 构建一次，预发布和生产运行同一个镜像
  - 预发布站点 `staging.antelacus.com`：和生产同一台 VPS、同一套 nginx + Cloudflare，只对 Jason 和 CI 开放；读生产数据，不能写
  - 合并即晋升；部署后自动核验，失败自动回滚；另有手动回滚
  - 迁移只做加法，删除或改名须标为收缩步；缺迁移拒绝部署；迁移由 Claude 在备份新鲜的前提下执行并核对
  - 后台读取改用登录会话 + 行级权限；管理员身份存进数据库
  - 每个改动只跑一遍闸门；耗时可读出
  - 覆盖补强：TD-021 的弱断言；后台的上传（端到端）、登出，以及其余内容类型
  - 手动清单自动化：打 tag、清 Cloudflare 缓存、核对 Auth 设置
  - 发布手册：`docs/DEPLOYMENT.md` 写明发布的每一步
- 明确不做：
  - CI 搬到 VPS 上（自托管 runner）
  - 镜像仓库：镜像只经部署 SSH 传到 VPS
  - 蓝绿 / 金丝雀发布、k8s、功能开关、独立 QA 环境、单独的预发布数据库
  - 预发布上的自动登录检查：登录后的后台由 Jason 手动看
  - 对生产写数据的端到端测试
  - 紧急修复的旁路：紧急修复同样经过预发布，止血靠手动回滚
  - 由 CI 执行生产迁移（生产迁移由 Claude 执行，§5.7）

## 2 上下文图
Jason 在笔记本上 push 一个分支 → GitHub Actions 跑闸门、构建镜像 → 经部署 SSH 把镜像交给 VPS → VPS 上的预发布容器运行它 → Cloudflare（Access）→ nginx → Jason 的手机和电脑，以及 CI 的检查。Jason 合并 PR → 同一个镜像在生产容器上运行 → Cloudflare → nginx → 访客。预发布和生产读同一个 Supabase 项目；只有生产持有写权限。生产数据库的迁移由 Claude 经 Supabase MCP 执行。

## 3 用例
- Jason push 一个分支：闸门过了，几分钟后 `staging.antelacus.com` 上就是这个提交。他用 iPhone 打开，看真实文章，登录后台看草稿。
- Jason 合并 PR：生产换成预发布验过的那个镜像，不重新构建。核验通过后自动打 tag。
- 部署后核验失败：生产自动退回上一个镜像，运行变红，GitHub 发邮件给 Jason。
- 上线几天后发现问题：Jason 手动把生产退回最近 5 个镜像中的任意一个。
- 一个需要新表的版本：Claude 确认备份新鲜后执行迁移、核对结果，再 push。push 早于迁移时，预发布部署拒绝，并说明缺哪条迁移。
- 生产着火：先手动回滚止血，修复照常经过预发布。

## 5 功能需求

### 5.1 无密钥的产物（F1）
- 规则：镜像里不含任何 `.env*` 文件，也不含任何密钥的值。构建所需的公开值以构建参数传入。镜像只在 CI 构建，VPS 上任何部署路径都不执行 `docker build`。
- 规则：镜像以**构建输入键**标记：它由参与构建的文件算出，`docs/**` 和 `*.md` 不参与构建。键相同的两个提交共用一个镜像。
- 硬错误：构建时缺少任一必需的公开值 → 构建失败，并报出缺少的变量名。
- 验收判据：
  - §5.1-a 用一个含标记密钥的假 `.env` 构建，最终镜像的文件系统里找不到 `.env*` 文件，也找不到这个标记。
  - §5.1-b 只在 `docs/**` 或 `*.md` 上不同的两个提交，算出同一个构建输入键；其余任何文件不同，键就不同。
  - §5.1-c 部署工作流和部署脚本里不出现 `docker build`、`compose … --build`。

### 5.2 传输与保留（F2）
- 规则：镜像经现有的部署 SSH 密钥交给 VPS，不用镜像仓库，不新增凭据。VPS 保留最近 5 个部署到生产的镜像，外加预发布正在用的那个；更早的删除。
- 验收判据：
  - §5.2-a 按保留规则算，连续 6 次生产部署之后，留下的正好是最近 5 个生产镜像；预发布正在用的镜像，任何时候都不会被删。

### 5.3 预发布站点（F3）
- 规则：地址 `staging.antelacus.com`，与生产在同一台 VPS、同一套 nginx，同样只放行 Cloudflare 的 IP。Cloudflare Access 只放行 Jason（邮箱验证码）和 CI（service token）。每个响应都带 `X-Robots-Tag: noindex`。常驻运行。环境里有生产 Supabase 的公开值，**没有** service-role 密钥。
- 规则：任何分支 push 过了闸门，它的镜像就自动部署到预发布，后到的覆盖先到的。另可手动指定一个 SHA 部署。
- 验收判据：
  - §5.3-a 不带 Access 凭据访问预发布，得到的是 Cloudflare Access 的登录跳转，请求到不了源站。
  - §5.3-b 带 service token 访问预发布，每个响应都有 `X-Robots-Tag: noindex`。
  - §5.3-c 预发布容器的环境里没有 `SUPABASE_SERVICE_ROLE_KEY`。
  - §5.3-d 一个非 main 分支 push 并过了闸门之后，预发布报出的构建标识就是这个提交的构建输入键；手动指定 SHA 部署后，报出的是那个 SHA 的键。

### 5.4 预发布检查与合并条件（F4）
- 规则：预发布部署完成后，自动经公网地址（带 service token）跑有库运行时套件，以及 §5.7 的迁移核对。只做匿名访问。结果作为那个提交的状态，是合并的必需检查。
- 规则：合并前分支必须与 main 同步。PR 模板里有一个勾选框：「已用手机登录预发布看过后台」。机器不强制它。
- 验收判据：
  - §5.4-a 预发布检查缺失或为红时，PR 无法合并（以分支保护的设置读出为证）。
  - §5.4-b 分支落后于 main 时，PR 无法合并（同上）。
  - §5.4-c PR 模板里有登录后台的勾选框。

### 5.5 晋升与部署后核验（F5）
- 规则：合并到 main 就是晋升。main 的 push 不跑闸门、不重新构建：按合并提交的构建输入键找到已有的镜像，部署到生产。键与生产当前的相同时（只改了文档），什么都不做。
- 规则：部署后经公网地址 `https://www.antelacus.com` 核验：
  - 报出的构建标识等于这次的键；
  - 有库运行时套件全绿。

  任一项失败 → §5.6 自动回滚。
- 规则：核验通过后：
  - `package.json` 的版本号与上一个生产镜像不同，就在合并提交上打 `v<版本>` tag；
  - 这次与上一个生产镜像之间，分享图（`/og.png` 路由、`public/og.png`）或 `public/images/` 有变化，就清除 Cloudflare 上这些路径的缓存；
  - 读 Supabase Auth 的公开设置：「允许注册」开着，或「邮箱确认」关着 → 这一项单独变红（GitHub 发邮件），**不回滚**。
- 硬错误：找不到这个键的镜像 → 拒绝部署，报「这个提交没有经过预发布的镜像；先 push 分支」。
- 验收判据：
  - §5.5-a main 的 push 触发零次闸门运行、零次镜像构建。
  - §5.5-b 部署之后，公网报出的构建标识等于合并提交的构建输入键。
  - §5.5-c 只改了 `docs/**` 的合并，不替换生产容器。
  - §5.5-d 版本号变了的部署在核验通过后留下 `v<版本>` tag；没变的不打。
  - §5.5-e 清缓存只在上述路径有变化时发生（按「哪些路径变了」算，可以单独测）。
  - §5.5-f 「允许注册」开着时，Auth 核对变红，生产不回滚。

### 5.6 回滚（F6）
- 规则：自动回滚把生产换回上一个生产镜像，再核验一次；运行最终为红。手动回滚可以选任一保留的镜像，同样经过核验。回滚从不碰数据库；坏版本在线期间写入的数据不会被撤销。
- 验收判据：
  - §5.6-a 在预发布上演练：部署一个核验必然失败的镜像，结束时报出的是上一个镜像的构建标识，运行为红。生产与预发布走同一套部署逻辑，只是参数不同。
  - §5.6-b 手动回滚到一个保留的镜像之后，报出的构建标识就是它。

### 5.7 迁移纪律（F7）
- 规则：迁移只做加法。含 `drop`、`rename`、`alter … type`、`truncate` 的迁移，必须带收缩步标注，写明它删的东西在哪个已发布的版本里停止了使用。否则闸门红。
- 规则：生产迁移由 Claude 执行、由 Claude 核对，不需要逐次征求 Jason 同意，经本项目的 Supabase MCP（可写，限本项目）。CI 从不执行迁移。每次按这个顺序：
  1. VPS 上最近一次备份不超过 26 小时，否则先在 VPS 上跑一次备份；
  2. 迁移只做加法，或带收缩步标注；
  3. 以迁移的文件名为名执行，留下执行记录；
  4. 从执行记录和表结构核对结果。

  核对只读结构和计数，不读行内容。迁移要在需要它的代码 push 之前执行。迁移以外的写库 SQL 不在授权范围内。
- 规则：预发布和生产部署前，只读核对仓库里的每条迁移在生产都有执行记录，缺一条就拒绝部署，并报出迁移的文件名。
- 验收判据：
  - §5.7-a 含 `drop column` 而没有收缩步标注的迁移让闸门变红；带标注的通过。
  - §5.7-b 仓库里有一条生产没有执行记录的迁移时，部署拒绝，报出的正是那个文件名。
  - §5.7-c 以前在 SQL 编辑器里执行的 7 条迁移补登了执行记录（只写记录，不重新执行）；此后每条迁移在执行记录里都能按文件名查到。

### 5.8 后台读取与管理员身份（F8）
- 规则：管理员身份用 Supabase 用户的 `app_metadata.role = admin` 表示（只有 service-role 能改），应用和行级权限都只读这一处；`SUPABASE_ADMIN_EMAILS` 退役。
- 规则：管理员经行级权限读全部内容，包括草稿、关于页各语言、关系表。后台的读取用登录会话；写入（保存函数、上传）只走 service-role。没有 service-role 密钥时，后台能登录、能看，保存明确失败。
- 硬错误：没有 service-role 密钥时保存 → 页面显示 `Read-only environment — not saved.`（后台界面是英文），不是 500。
- 验收判据：
  - §5.8-a 行级权限：已登录的非管理员读不到草稿；管理员读得到（在一次性 Postgres 上验证）。
  - §5.8-b 没有 service-role 密钥时，后台的总览、列表、编辑器都能以管理员身份打开，并显示草稿。
  - §5.8-c 没有 service-role 密钥时保存，显示只读提示，数据不变。
  - §5.8-d service-role 客户端只出现在写入路径上（测试强制）。

### 5.9 闸门只跑一遍（F9）
- 规则：闸门只在分支 push 上跑；PR 显示同一个 SHA 上的结果，不另跑。有库全量已覆盖的检查不再单独跑一遍，`db-function-check.sh` 进闸门。每次运行把各任务、各步骤，以及部署各段（传输、启动、核验）的耗时写进运行摘要。
- 验收判据：
  - §5.9-a 一次分支 push 恰好产生一次闸门运行；开 PR 不产生新的运行。
  - §5.9-b 闸门里运行 `db-function-check.sh`。
  - §5.9-c 闸门和部署的运行摘要里有每一步的耗时。

### 5.10 覆盖补强（F10）
- 规则：TD-021 列出的每条运行时检查，都要改到能在它点名的情形下失败。后台界面检查补上：上传（合成环境里打开存储服务：上传 → 文件进存储桶 → 页面显示出来）、登出、其余内容类型和关于页的列表与编辑器。
- 验收判据：
  - §5.10-a TD-021 里的每一条，都各有一次「植入它点名的情形 → 检查变红」的证据。
  - §5.10-b 在合成环境里上传一张图，它会出现在存储桶里，在页面上加载成功。
  - §5.10-c 登出之后访问后台，会被带到登录页。
  - §5.10-d 后台的每种内容类型和关于页，都有列表与编辑器的界面检查。

### 5.11 发布手册（F11）
- 规则：`docs/DEPLOYMENT.md` 按顺序写明一次发布要人或 Claude 动手、或要读结果做判断的每一步：push 与预发布、登录后台看一眼、迁移（指向项目 `CLAUDE.md`）、合并与生产核验、自动回滚之后做什么、手动回滚、发布后的收尾。CI 自动完成的部分只写在哪里看结果，不复述它怎么做。
- 验收判据：
  - §5.11-a Phase 4 的那次真实发布完全照手册执行，中途不需要翻手册以外的任何地方；卡住的地方当场补进手册。

## 6 其他需求
- **The Floor**：
  - 预发布不持有 service-role 密钥（§5.3-c）；
  - 镜像不含密钥（§5.1-a），不含之前镜像不离开 VPS；
  - 本版新增的凭据只有两个：Cloudflare Access 的 service token，和只有本站清缓存权限的 Cloudflare 令牌。都放在 GitHub secrets 里，各经 Jason 批准；
  - 没有能写生产数据的凭据进入 CI；
  - 常驻的写库能力只有一处：本项目的 Supabase MCP（可写，限本项目、限数据库与文档两组工具）。免确认的只有迁移和只读核对工具，其余写库 SQL 仍要逐次确认；
  - 外发检查照旧：生产数据进了上下文，往外送任何东西之前都要先停下。
- **可用性**：生产切换镜像时的中断不长于现在的 `compose up`；预发布的任何故障都不影响生产容器。
- **可缓存**：公开页面仍按 routing-slimdown §5.3 保持可缓存；预发布同样适用。

## 7 对外接口
- **构建标识**：生产和预发布都通过公网报出当前镜像的构建输入键，形式由 DESIGN 定。读者是部署核验和 Jason。
- **GitHub**：沿用现有的部署 SSH secrets；新增 Access service token 和清缓存令牌两个 secrets。分支保护：必需的预发布检查，分支须与 main 同步。
